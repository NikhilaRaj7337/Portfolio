SmartStay: two-stage retrieval and ranking for travel search

A recommender that narrows 20,331 real New York City listings to 200 candidates with a Two-Tower network and FAISS, then orders them with a LightGBM LambdaMART ranker, served behind FastAPI.

The problem

Search ranking at marketplace scale can't run an expensive model over every item for every request. Production systems split the job in two. A cheap, high-recall retrieval stage covers the whole catalog, and a feature-rich ranking stage orders a few hundred candidates.

I wanted to build that architecture end to end, measure whether each stage earns its place against simple baselines, and serve it behind an API with tests and CI.

The data, and what's simulated

Listings come from Inside Airbnb for New York City: about 30,234 raw rows, cut to 20,331 after removing listings with no current price. Each row is validated with pandera before it enters the pipeline.

Simulated interactions. Public listing data has no searches, clicks or bookings. I generated user personas and simulated search sessions against the real listings, using a hidden utility function (price fit, location, room type, quality, popularity, noise) to decide what each user views, clicks and books. The listings are real; the engagement signal is not.

That gave 84,057 training and 10,504 validation positive pairs for the retrieval model.

Architecture

Stage 1: Two-Tower retrieval

A user tower and an item tower embed requests and listings into one space. Because the item side doesn't depend on the user, every listing is embedded once offline and indexed in FAISS. At request time only the user tower runs, followed by a nearest-neighbor search that returns 200 candidates.

Stage 2: Learning to rank

A LightGBM LambdaMART model, which optimizes NDCG directly, reorders the 200 candidates using engineered features: price fit, distance, popularity and the retrieval score itself. A PyTorch neural ranker is trained alongside it for comparison.

Serving and tooling

A shared feature store keeps training and serving features identical. FastAPI serves POST /recommend. MLflow tracks experiments, Docker images cover training and serving, and GitHub Actions runs lint, the pytest suite (all offline against a committed 500-listing fixture) and Docker builds.

One held-out item per user among 20,331 listings makes this a hard task: chance Recall@20 is about 20 / 20,331 ≈ 0.001. That's why both baselines sit near zero.

The learned retriever wins clearly and consistently: it roughly doubles NDCG at every cutoff and multiplies MRR@20 by 2.5 over the content-based baseline. Hand-crafted similarity misses personalization signal that the embedding space captures.

The full two-stage system is more mixed. The reranker lifts Recall@10 by 42% over plain retrieval (0.0017 vs. 0.0012) and improves NDCG@20, but Recall@5, NDCG@5 and MRR@20 fall back toward the baseline. It pulls more relevant listings into the top 10–20 without yet picking the single best one for positions 1–5.

What I learned

  • Baselines keep you honest. Without popularity and content-based rows on the same split, the tiny absolute numbers would be impossible to read.
  • A second stage isn't free. The reranker helped recall at 10–20 and hurt the very top. My hypothesis is that its engineered features add little beyond the retrieval score, so it mostly reshuffles retrieval's own ordering.
  • Train/serve parity needs structure. Putting featurization in one shared module means the API computes features with exactly the code used in training.

Next steps

  • Inspect LightGBM feature importance to test the reranker hypothesis, then add user-listing interaction features.
  • Try pairwise or listwise loss for the neural ranker.
  • Profile the HTTP path to close the gap between 1 ms model time and 227 ms request time.
  • Run larger hyperparameter sweeps tracked in MLflow, and test on a second city.
